# November 2026

## [November 17, 2026] Added Reality Public Fills WebSocket Channel; Added `execVenue` Execution Venue Identifier to Fill Data

**New WebSocket channel:**

- [Reality Fills Channel](/docs/uta/websocket/reality/public/Reality-Fills-Channel) (public channel, topic `reality-fills`): pushes real-time fill data (internal + lit market) for Reality (rToken) trading pairs, with the execution venue identifier `execVenue`

Interface:
- REST: `GET` /api/v3/account/reality-fills
- REST: `GET` /api/v3/trade/fills
- WebSocket: Fast Fill Channel (`fast-fill`)

Changes:
- `/api/v3/account/reality-fills`: added `execVenue` String response parameter
- `/api/v3/trade/fills`: added `execVenue` String response parameter and optional `execVenue` request parameter for filtering
- Fast Fill Channel: added `execVenue` String push parameter
- `execVenue` values: `internal_market` internal fill (matched in the internal order book); `lit_market` lit market fill (routed to an external broker). Only returned for Reality (rToken) fills; empty string for other business lines
- Migration: the general public trades channel and REST API no longer return fills of Reality (rToken) trading pairs. Please migrate to the Reality Fills Channel or `/api/v3/account/reality-fills`

## [November 5, 2026] Notice: Adjustment to rToken Order Routing Strategy (`venue`) Enum Values

- Effective date: November 5, 2026

The enum values of the `venue` (order routing strategy) parameter in the rToken order placement and order query APIs (REST and WebSocket) are adjusted as follows:

| **Before** | **After** | **Description** |
|:-|:-|:-|
| internalization | internal_market | Orders are matched within the exchange and are not submitted to the U.S. stock broker |
| - | lit_market | Orders are submitted to the U.S. stock broker and are not matched within the exchange |
| lit_market | Omitted / default | Orders are first matched internally within the exchange at the best price; any unfilled portion is submitted to the broker |

**Important Notes:**

1. `internalization` is renamed to `internal_market` with no change in meaning: "orders are matched within the exchange and are not submitted to the U.S. stock broker." Please replace this enum value with `internal_market`.
2. Orders previously shown as `lit_market` in order details will be shown as `default` after the adjustment, meaning "orders are first matched internally within the exchange at the best price; any unfilled portion is submitted to the broker." Please update the parsing logic for order details on your side accordingly.
3. The new `lit_market` means "orders are submitted to the broker for execution and are not matched within the exchange." This differs from the meaning of `lit_market` shown in order details before the adjustment, so please distinguish between the two carefully.
4. Omitting `venue` when placing an order applies the default strategy. The accepted enum values for the order placement API are `internal_market` and `lit_market`.
5. The `venue` field returned in order details will consistently use the adjusted enum values.

Please adjust the `venue` parameter according to your trading strategy. For detailed routing and matching rules, please refer to the [rToken Trading Guide](/docs/uta/reality-trading-guide).<br/>
If you encounter any parameter validation or enum parsing issues after November 5, please contact us promptly and we will be happy to assist.

## [November 2, 2026] FastAPI Signature Algorithm Upgrade

- Release date: November 3, 2026

The FastAPI request signature algorithm is being upgraded from MD5withRSA to SHA256withRSA. You only need to change the hash algorithm from MD5 to SHA-256 in both your request-signing code and your callback signature verification code. For example, in Java, replace Signature.getInstance("MD5withRSA") with Signature.getInstance("SHA256withRSA"); the same applies to other languages. The estimated effort is under one hour, plus sandbox testing.<br/>
For code examples of signing and RSA encryption/decryption, please refer to the [FastAPI Integration Guide](https://www.bitget.com/docs/uta/fastapi-integration-guide#code-examples-java)<br/>
For the detailed migration timeline, please refer to [Bitget FastAPI Signature Algorithm Upgrade Notice](https://www.bitget.com/support/articles/12560603899220)

## [11月5日, 2026] rToken 订单路由策略（venue）枚举调整公告

- 生效时间：2026 年 11 月 5 日

rToken 下单及订单查询接口（REST、WebSocket）的 `venue`（订单路由策略）参数枚举调整如下：<br/>

| **调整前** | **调整后** | **说明** |
|:-|:-|:-|
| internalization | internal_market | 订单在交易所内撮合，不提交美股券商 |
| - | lit_market | 订单提交至美股券商，不在交易所内撮合 |
| lit_market | 不传/default | 优先交易所内部比价撮合，未成交部分提交至券商 |

**重要提示：**<br/>
1. `internalization` 更名为 `internal_market`，含义不变，含义为"订单在交易所内撮合，不提交美股券商"。请将该枚举值替换为 `internal_market`。<br/>
2. 订单详情中原本展示为 `lit_market` 的订单，调整后展示为 `default`，含义为"优先交易所内部比价撮合，未成交部分提交至券商"。请同步更新您侧订单详情的结果解析逻辑。<br/>
3. 新的 `lit_market` 含义为"订单提交至券商执行，不在交易所内撮合"，与调整前订单详情展示的 `lit_market` 含义不同，请注意区分。<br/>
4. 下单时不传 `venue` 即为默认策略；下单接口可传入的枚举值为 `internal_market` 或 `lit_market`。<br/>
5. 订单详情返回的 `venue` 将统一使用调整后的枚举值。<br/>

请您根据自身交易策略评估并调整 venue 参数的使用方式，以确保订单按预期路由。详细的路由与撮合规则请参考 [rToken 交易指南](/zh-CN/docs/uta/reality-trading-guide)。<br/>
如您在 11 月 5 日后遇到参数校验或枚举解析异常，请及时与我们联系，我们将提供协助。
